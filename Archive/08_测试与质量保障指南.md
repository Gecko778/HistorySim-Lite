# 测试与质量保障指南

## 一、测试目标

测试的目标是证明 HistorySim Lite 能够稳定、可解释、可复现地运行。测试不只检查界面是否可点击，还应检查核心算法、状态更新、AI 决策、事件触发和存档恢复是否正确。

## 二、测试范围

| 测试类型 | 覆盖对象 |
|---|---|
| 单元测试 | 地图、路径、资源、战斗、AI、事件、命令校验 |
| 集成测试 | 回合推进、命令执行、AI 行动、事件触发 |
| 边界测试 | 非法命令、无路可达、资源不足、负数风险 |
| 复现测试 | 固定随机种子下的战斗和事件 |
| UI 测试 | 地图选择、命令输入、日志查看、存档读档 |
| 数据测试 | ID 唯一、引用有效、地图连通、数值范围 |

## 三、单元测试要求

### UT-01 地图连通性测试

目标：确认 30 个地区组成连通图。  
输入：地区邻接表。  
期望：从任意一个地区出发，可以访问全部 30 个地区。

### UT-02 可达性测试

目标：验证 BFS 可达性查询。  
输入：起点地区和最大步数。  
期望：返回指定步数内可达的地区集合。

### UT-03 最低成本路径测试

目标：验证 Dijkstra 路径结果。  
输入：起点、终点、地形成本表。  
期望：返回成本最低路径和总成本。

### UT-04 开发公式测试

目标：验证 DEVELOP 命令对地区数值的影响。  
输入：地区状态、太守政治属性、技能修正。  
期望：农业、商业、城防或治安按公式增长，且不超过上限。

### UT-05 征兵公式测试

目标：验证 RECRUIT 命令的资源消耗与兵力增长。  
输入：人口、金钱、粮草、征兵规模。  
期望：兵力增加，人口和资源减少，非法征兵被拒绝。

### UT-06 任命测试

目标：验证 APPOINT 命令。  
输入：人物、地区或军队。  
期望：人物被正确任命，并影响后续开发或战斗。

### UT-07 战斗结算测试

目标：验证 ATTACK 命令和战斗公式。  
输入：攻击方、防守方、地形、城防、随机种子。  
期望：产生胜负、伤亡、士气变化和日志。

### UT-08 AI 评分测试

目标：验证 AI 候选行动评分。  
输入：势力状态、相邻地区、资源状况。  
期望：AI 能给出合理排序，资源不足时不会优先发起高风险攻击。

### UT-09 事件触发测试

目标：验证事件条件与效果。  
输入：满足条件的 GameState。  
期望：事件被触发并正确修改状态。

### UT-10 存档读档测试

目标：验证 GameState 保存和恢复。  
输入：某一回合状态。  
期望：读档后回合号、随机种子、地区、势力、人物和日志一致。

## 四、集成测试要求

### IT-01 单回合推进测试

执行一个完整回合，检查玩家命令、AI 命令、资源结算、事件和日志是否按顺序完成。

### IT-02 20 回合连续模拟测试

从初始剧本开始连续推进 20 回合。系统不得崩溃，关键数值不得出现负数或非法状态。

### IT-03 玩家攻击流程测试

玩家从选择地区、移动军队、攻击敌方地区到查看战斗日志，形成完整流程。

### IT-04 AI 自动对局测试

在无玩家干预或最小玩家干预下，AI 势力能持续行动，系统能输出 AI 决策日志。

### IT-05 存档恢复后继续模拟测试

在第 10 回合存档，读档后继续运行至第 20 回合，状态推进正常。

## 五、边界测试要求

| 场景 | 期望处理 |
|---|---|
| 攻击己方地区 | 拒绝命令并输出错误 |
| 攻击不可达地区 | 拒绝命令并说明原因 |
| 资源不足时征兵 | 拒绝命令或降低执行规模 |
| 无太守时开发 | 使用基础增长，不应用太守加成 |
| 人物死亡后任命 | 拒绝命令 |
| 事件重复触发 | 按事件规则限制触发次数 |
| 战斗后兵力为负 | 自动截断为 0 并记录异常修正 |
| 地区无所属势力 | 数据校验失败 |
| 地图不连通 | 数据校验失败 |
| 存档版本不一致 | 给出提示，禁止直接加载 |

## 六、复现测试要求

固定随机种子后，以下结果应可复现：

1. 战斗胜负；
2. 战斗伤亡；
3. 随机事件触发结果；
4. AI 候选行动排序；
5. 20 回合模拟摘要。

测试报告中应记录随机种子、初始剧本版本、命令序列和测试结果。

## 七、测试报告结构

TEST_REPORT.md 应包含：

1. 测试环境；
2. 测试范围；
3. 单元测试结果；
4. 集成测试结果；
5. 边界测试结果；
6. 复现测试结果；
7. 缺陷记录；
8. 修复记录；
9. 测试结论。

## 八、质量保障要求

1. 每次阶段提交前至少运行相关测试；
2. 所有核心算法修改后必须补充或更新测试；
3. 发现缺陷后应记录复现步骤；
4. 不得只依赖界面手工点击验证系统；
5. 答辩时应展示至少 3 个测试案例；
6. 测试报告应与实际系统一致。
