# HistorySim Lite 需求与范围说明

## 一、系统目标

HistorySim Lite 是一个教学用途的历史策略模拟系统。系统以地区、势力、人物、军队、技能和事件为核心对象，通过回合制规则推动世界状态变化。系统应提供简单 UI，支持地图查看、地区选择、人物任命、命令输入、回合推进和日志查看。

本系统不追求商业游戏的美术质量、复杂动画或实时战斗效果。其重点是数据建模、算法实现、状态演算、软件架构和工程验证。

## 二、角色

| 角色 | 说明 |
|---|---|
| 玩家（Player） | 操作一个势力，执行开发、征兵、移动、攻击和任命等命令 |
| AI 势力（AI Faction） | 由系统根据效用评分自动生成行动 |
| 教师（Instructor） | 检查项目结果、运行测试、评价算法与架构质量 |
| 学生开发者（Student Developer） | 按任务书完成系统开发和文档编写 |

## 三、核心对象

| 对象 | 英文名 | 说明 |
|---|---|---|
| 地区 | Region | 地图上的基本节点，表示城池、郡县或据点 |
| 势力 | Faction | 控制地区和人物的政治或军事集团 |
| 人物 | Person | 具有属性、忠诚、技能和所属关系的历史人物 |
| 军队 | Army | 可移动和参与战斗的兵力单位 |
| 技能 | Skill | 对内政、战斗、AI 或事件产生影响的能力 |
| 事件 | Event | 在满足条件时触发的状态变化 |
| 命令 | Command | 玩家或 AI 对系统提交的行动请求 |
| 世界状态 | GameState | 当前回合的完整系统状态 |

## 四、标准数据规模

最终作品必须使用统一标准规模：

| 数据项 | 数量 |
|---|---:|
| Region | 30 |
| Faction | 4 |
| Person | 50 |
| Skill | 20 |
| Event | 10 |

地区之间必须形成连通图。至少应包含 40 条地区连接关系。每个势力初始至少控制 3 个地区。每个势力初始至少拥有 8 名人物。

## 五、功能需求

### FR-01 地图展示

系统应显示 30 个地区，并通过颜色表示地区所属势力。用户可以选择某个地区查看详细信息。地图表现形式可以为简化区域图、节点连接图、SVG 图、Canvas 图或 PixiJS 图层。

### FR-02 地区信息管理

系统应显示地区的名称、所属势力、人口、农业、商业、治安、城防、驻军、粮草和相邻地区。地区数据应参与资源增长、征兵、战斗和 AI 评估。

### FR-03 势力信息管理

系统应显示势力名称、君主、控制地区数量、总人口、总兵力、金钱、粮草和外交状态。AI 势力应根据自身状态生成行动。

### FR-04 人物信息管理

系统应显示人物姓名、所属势力、所在地区、年龄、状态、五项能力、忠诚、野心和技能。五项能力固定为统率（Command）、武力（Strength）、智力（Intelligence）、政治（Politics）、魅力（Charisma）。

### FR-05 基础命令系统

系统必须支持以下 5 类命令：

| 命令 | 英文标识 | 功能 |
|---|---|---|
| 开发 | DEVELOP | 提升地区农业、商业或城防 |
| 征兵 | RECRUIT | 将人口和资源转化为兵力 |
| 移动 | MOVE_ARMY | 将军队从一个地区移动至相邻或可达地区 |
| 攻击 | ATTACK | 对敌对势力控制地区发起战斗 |
| 任命 | APPOINT | 任命人物为地区太守或军队将领 |

### FR-06 回合推进

系统应按固定阶段推进回合。建议阶段为：命令收集、命令校验、玩家命令执行、AI 行动生成、AI 命令执行、资源结算、战斗结算、事件触发、人物状态更新、日志生成、状态保存。

### FR-07 战斗结算

系统应支持抽象战斗结算。战斗结果应由兵力、将领统率、士气、地形、城防、技能和随机波动共同影响。随机过程必须支持固定随机种子，以便复现实验结果。

### FR-08 AI 行动

AI 势力每回合至少能够完成 1 至 3 个行动。AI 行动应基于效用评分函数产生，不能完全随机。AI 应能在发展、征兵、防守和攻击之间进行选择。

### FR-09 事件系统

系统应支持 10 个事件，包括历史事件和随机事件。事件应具有触发条件、影响对象、效果和日志描述。事件效果应能改变地区、势力、人物或军队状态。

### FR-10 日志与存档

系统应记录每回合关键变化，包括命令执行结果、战斗结果、资源变化、事件触发和 AI 决策说明。系统应支持保存和读取 GameState。存档至少应包含当前回合、随机种子、世界状态和日志摘要。

## 六、非功能需求

| 编号 | 要求 | 说明 |
|---|---|---|
| NFR-01 | 可测试性 | 模拟内核应能脱离 UI 运行和测试 |
| NFR-02 | 可复现性 | 同一初始状态、命令序列和随机种子应产生相同结果 |
| NFR-03 | 可维护性 | 地图、战斗、AI、事件、存档应拆分为独立模块 |
| NFR-04 | 可扩展性 | 技能和事件应尽量配置化，不应全部写死在回合流程中 |
| NFR-05 | 可解释性 | 战斗、AI 和事件结果应有日志说明 |
| NFR-06 | 教学可控性 | 功能范围不得超出标准规模，避免项目失控 |

## 七、范围外内容

以下内容不纳入课程基本要求：

1. 复杂实时战斗画面；
2. 联网对战；
3. 商业级美术资源；
4. 大规模历史数据库；
5. 深度学习；
6. 多语言国际化；
7. 移动端适配；
8. 完整剧本编辑器。

上述内容可作为挑战任务，但不得影响必做功能交付。
